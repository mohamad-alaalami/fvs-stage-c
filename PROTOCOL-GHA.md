# Stage C on GitHub Actions: protocol and deviations

The counting definitions are unchanged from `records/local-stage-c/PROTOCOL.md`: B, T, A, the Cao, Chen and LP candidate rules, the Chen qualifying-state and invariant predicates, the snapshot schema `STAGEC1`, and the replay rule (largest completed A continuation with at most 1000 decisions, original pivot, original continuation, trace length, trace digest and final-state digest compared). The instrumented source edits (`prepare.py`) and `StageC.h` are byte-identical to the local edition. Only `StageC.cpp`'s output plumbing differs.

## Differences from the local batch

1. **Machine.** GitHub-hosted `windows-latest` runners. Each pair's baseline and instrumented runs share one runner, so the overhead ratio is within-machine. Different pairs may run on different hardware; the CPU model is recorded per build and in every row. The local laptop runs (`records/local-stage-c`) are preserved and are **not merged** with this batch. This batch reruns 095 and 029/8 from scratch for consistency.
2. **Storage: segmented streams with lossless compression.** Snapshots, events and continuation records are written to 256 MiB segment files. A sidecar (three threads) compresses each closed segment with zlib level 6. It decompresses the result and checks length and SHA-256 before deleting the raw segment, and logs every segment to `manifest.jsonl`. Concatenating the decompressed segments reproduces the local single-file streams byte for byte, verified on 095 for all three solvers. Nothing is sampled or dropped. `snapshot_bytes` and `log_bytes` are logical (uncompressed) sizes; `*_stored_bytes` are the on-disk sizes.
3. **Reserve.** The reserve is 3 GiB of free space on the runner's output volume. The laptop used 10 GiB; a disposable runner needs only enough to keep the OS and the artifact upload working. The clean-stop rule is unchanged: the solver refuses a snapshot unless free space exceeds reserve + snapshot + 1 MiB, and the monitor stops at reserve + 64 MiB. A reserve stop ends **that run** (`disk_reserve`) with partial records and its growth rate; other pairs run on their own runners. This per-run behaviour was approved.
4. **Scheduling.** One job per (graph, solver), up to 20 in parallel (parallelism approved; per-pair jobs give each pair a fresh disk). Within a job the order is baseline, verify, instrumented, verify, audit, replay.
5. **Job deadline.** If a job reaches 5 h of wall time (GitHub's job limit is 6 h), the active run is stopped cooperatively with status `job_deadline` and its partial records are kept. Not-yet-started runs are marked `not_run_job_deadline`.
6. **Build.** The same w64devkit 2.11.0 archive (GCC 16.2.0, SHA-256 checked) and the same effective flags `-include string -std=c++11 -O3`, with assertions on. g++ is called directly rather than through CMake/Ninja.
7. **Audit.** Every run uses the native `SnapshotCheck`. Python streams it every event line plus each A event's snapshot bytes from the segments, and independently recounts B/T/A, checks that snapshot offsets are contiguous, and checks for unreferenced snapshot bytes. An audit failure is recorded in the row (`audit=fail` with the reason) instead of aborting the remaining work.
8. **Wall-time caveat.** The compression sidecar shares the runner's cores. Process CPU time (the 1800 s limit and the overhead ratio) is per process and is barely affected, but instrumented wall time includes this contention.

## Local load test before launch (laptop, 029/8, 30 s CPU limit)

806,136 B = T events; A = 484,262 snapshots; 3,569,318,635 logical bytes were stored as 135,221,474 bytes (26.4×). The native audit passed for all 484,262 snapshots, and the replay check passed. At this growth rate (about 119 MB per CPU-second here), a full 1800 s run of 029/8 would produce roughly 200 GB logical, about 7 GB stored. That is an estimate, not a measurement.
